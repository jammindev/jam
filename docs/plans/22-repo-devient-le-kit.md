## 1. Objectif et critère de fin

Le repo cesse d'être une app et devient le plugin : app retirée, quatre hooks rapatriés avec leurs tests (dont une **garde de sortie unique**), deux scripts, installation décidée (Q-055), fiche concept.

Critère de fin (celui de l'issue) : `apps/` et `packages/` n'existent plus et la CI ne lance que les tests du kit ; les tests des hooks et des scripts passent en CI ; chargé par `--plugin-dir` depuis le worktree, le plugin câble les quatre hooks (récapitulatif marqué, refus marqué d'une écriture du coordinateur, d'un `git commit`, d'un `git push` et d'une écriture `gh` sans accord) ; aucun nom de personne, chemin du poste ni nom d'un autre projet dans `hooks/`, `scripts/` ni `.claude-plugin/` ; fiche concept écrite ; temps du mainteneur dans le corps de la PR.

## 2. Choix techniques

- **Python 3, bibliothèque standard seule**, tests `unittest` (02-ARCHITECTURE). Code compatible Python 3.9 (le `python3` système de macOS) : pas de `match`, pas d'annotations `X | Y`.
- **Découverte des tests** : `hooks/__init__.py` et `scripts/__init__.py` vides, pour que `python3 -m unittest` sans argument, depuis la racine, trouve tous les tests (la découverte ne descend que dans des paquets). Sous Python 3.12+, zéro test trouvé fait échouer la commande : la CI ne peut pas passer à vide.
- **Hooks lancés par `python3`**, jamais par leur bit exécutable (l'implémenteur n'a pas `chmod`). Câblage `hooks/hooks.json`, forme shell : `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/<hook>.py"`, même forme que le câblage actuel du poste. Les tests lancent les hooks par `sys.executable` ; un faux binaire Orca est écrit par le test lui-même dans un dossier temporaire (modèle : `test_session_start_recap.py`).
- **Binaire Orca** (ajustement a) : `JAM_ORCA_BIN` s'il est posé, sinon `orca` trouvé dans le `PATH` (`shutil.which`), sinon l'emplacement d'installation standard de l'app sur macOS (`/Applications/Orca.app/Contents/Resources/bin/orca`), générique et non propre au poste. Aucun autre chemin en dur. Cet emplacement est une constante du module que les tests remplacent, pour que « CLI Orca introuvable » se teste aussi sur un poste où Orca est installé.
- **Module de la CLI Orca** (ajustement b) : `scripts/orca_cli.py` porte la résolution du binaire et les appels à la CLI Orca, avec ses tests (`scripts/test_orca_cli.py`). `watch_cards.py`, `launch_task.py` et `session_start_recap.py` l'utilisent ; aucun ne résout le binaire lui-même.
- **Marque** : chaque message d'un hook ou d'un script du plugin commence par `[jam]`.
- **CI** : le job pnpm est remplacé par un job `ubuntu-latest` qui lance `python3 -m unittest` (Python et git du runner), `permissions: contents: read` et `timeout-minutes` gardés.
- **Schéma de la CLI Orca** : versionné **seulement pour ce que les scripts utilisent**, sous forme d'exemples de sorties (`scripts/fixtures/orca/*.json`) servis par le faux binaire des tests. C'est le contrat que les tests vérifient ; pas de copie du schéma complet, qui vieillirait sans être lu (la doc de référence reste `orca skills get orca-cli`). Cela répond à l'ADR 0017 (« versionné dans le plugin s'il est indispensable aux scripts »).
- **Q-055, tranchée ici (recommandation, question 1)** : **marketplace locale** sur le clone de jam du poste (son worktree principal), installée **pour tout le poste** (`--scope user`). Le repo porte `.claude-plugin/marketplace.json` (`"name": "jam"`, un seul plugin `{"name": "jam", "source": "."}`), fichier que l'issue ne liste pas mais qu'impose ce choix. Vérifié dans la doc de Claude Code : un plugin à source relative d'une marketplace ajoutée par chemin local est **chargé en place**, sans copie ; une modification de ses fichiers prend effet au démarrage de session suivant ou par `/reload-plugins`, quel que soit le champ `version`. **Mise à jour après un merge** : le `git pull` que fait déjà le coordinateur sur `main` suffit ; pas de `claude plugin update`, pas de `version` dans `plugin.json`. Écartée : l'installation depuis GitHub, copiée en cache et mise à jour par `claude plugin update` ou l'auto-update (désactivé par défaut hors marketplaces officielles, délai aléatoire jusqu'à dix minutes) : un correctif de garde arriverait en retard. Contrepartie : le worktree principal de jam doit rester sur `main`, ce qu'il fait (le coordinateur y vit et n'écrit pas de fichiers). Installation pour tout le poste confirmée : la garde de sortie vaut pour tous les projets du poste, ce que veut l'ADR 0016.
- **`--plugin-dir`, vérifié** (doc « Plugin loading reference ») : le plugin est chargé en place, pour la seule session lancée avec l'option (id `jam@inline`), sans toucher l'installation. Une fois le plugin installé (après K1-2), une copie `--plugin-dir` remplace pour cette session le plugin installé de même nom : la recette d'une tâche future teste bien la version du worktree.
- **Hooks du poste et du plugin coexistent** : tous les hooks qui correspondent tournent en parallèle. Pendant la recette, le poste affiche son propre récapitulatif et refuse aussi : seul ce qui porte `[jam]` compte.
- **`${CLAUDE_PLUGIN_ROOT}` n'est pas défini pour l'outil Bash** (doc) : un agent ne trouve pas seul les scripts du plugin. Pour K1-1, ils se lancent par leur chemin dans le worktree ; l'affichage de ce chemin revient à K1-2 (question 5).
- Aucune contradiction avec une ADR. La garde du coordinateur garde son exception « installation d'un hook relu » (Q-056, hors périmètre).

Lecture du même accord que l'annexe A (dernier message du mainteneur dans la session qui lance la commande). L'exemption `/tmp/claude-*` ne vaut que pour commit et push.
