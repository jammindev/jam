## Suggestions

1. **`scripts/maintainer_time.py:214`** — le nom du worktree est cherché comme sous-chaîne, sans borne : un message sur `cadrage-kit-2` est rattaché à `cadrage-kit`, un message sur `12-foo` à `2-foo`. Sans `--since`/`--until`, toute l'histoire des sessions de `main` est lue, donc deux noms emboîtés n'ont pas besoin d'être ouverts en même temps. Correction : borner le nom, par exemple `rf"(?<![\w-]){re.escape(nom)}(?![\w-])"`, et ajouter le cas au test de rattachement. Pas de scénario sur les noms actuels de jam, d'où la suggestion.
2. **`scripts/maintainer_time.py:78-88` et `:226`** — `--until 2026-10-12`, une date sans heure, vaut minuit au *début* du jour : tout le 12 tombe « hors fenêtre ». Le compte « hors fenêtre » du rapport le montre, mais c'est un piège pour le recetteur. Correction : soit l'écrire dans l'aide de `--until` (« une date seule vaut 00:00 »), soit étendre une date seule à la fin du jour ; tester les bornes (un message à l'heure exacte de `--since` ou `--until` est gardé : le code compare en `<` et `>`, aucun test ne le fixe, `scripts/test_maintainer_time.py:271`).
3. **`scripts/maintainer_time.py:119`** — les évènements sont regroupés par `sessionId` sans dédoublonnage. Si une reprise (`--continue`, que le coordinateur utilise) recopie l'historique dans un nouveau fichier, chaque message compte deux fois dans « message(s) retenu(s) » et dans le nombre de sessions lues ; les moments et le total ne bougent pas (mêmes horodatages). Je n'ai pas pu vérifier le format réel (lecture des transcripts interdite). Correction possible : écarter un évènement dont l'`uuid` a déjà été vu.
4. **`scripts/maintainer_time.py:185` et `process/README.md:112`** — une commande `/` du mainteneur compte comme un message (réduite à ses arguments, `""` sans argument) et peut être rattachée par le tour qui la précède ; le process ne cite que les commandes `!` comme non comptées. C'est défendable (le mainteneur a tapé quelque chose), mais non écrit : à dire en une demi-ligne dans la docstring, sans règle nouvelle.
5. **`scripts/test_watch_cards.py:196-233`** — les deux tests datés par `now_ms()` supposent que la première lecture arrive moins de 3 s après la création de la ligne. Marge confortable (deux démarrages d'interpréteur), mais un runner très chargé ferait échouer le test par `TimeoutExpired` sans dire pourquoi. Option : `--idle-minutes 0.1` (6 s) pour ces deux cas, ou un message d'échec qui nomme la cause.

Un sous-cas dans `test_unreadable_start_falls_back_to_script_clock` ou un test dédié suffit.
